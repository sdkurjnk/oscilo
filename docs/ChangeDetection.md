# 변경 감지 전략

실행되는 줄마다 추적 중인 변수가 바뀌었는지 판정하는 방식을 정리한다.

관련 코드: `VariableTracker.evaluate`, `VariableTracker._make_state`, `VariableTracker.get_snapshot`, `oscilo_engine.c`, `HistoryBuffer._serialize_entry`

---

## 전제: 판정은 줄마다 실행된다

oscilo는 추적 중인 프레임에서 줄이 실행될 때마다 이 판정을 한다. 그래서 판정 비용이 oscilo 전체의 오버헤드를 결정한다.

비용이 적은 검사를 먼저 하고, 거기서 결론이 나면 비싼 검사는 건너뛰도록 설계했다.

## 참조 모델

파이썬 변수는 값 자체가 아니라 힙에 있는 객체를 가리키는 참조다. 개념적으로는 `{변수명: 참조}` 형태의 네임스페이스로 볼 수 있지만, 실제로 참조가 저장되는 위치는 지역 변수와 전역 변수가 다르다.

지역 변수의 참조는 프레임 안의 `f_localsplus` 배열에 변수별 인덱스로 저장된다. `x = 10`을 실행하면 배열에서 `x`에 해당하는 슬롯(`0x010`)이 힙의 `10` 객체(`0x001`)를 가리킨다.

![지역 변수 x = 10 — 스택 슬롯이 힙의 객체를 가리킨다](assets/ChangeDetection/image_1.png)

재할당해도 힙의 기존 객체를 덮어쓰지 않는다. C와 달리 파이썬은 `x = 20`을 실행할 때 기존 객체의 값을 20으로 바꾸지 않는다. 힙에 새 객체를 만들고, 슬롯이 그 객체를 가리키도록 참조만 바꾼다. 슬롯(`f_localsplus[index]`)의 위치는 그대로다.

![재할당 x = 20 — 힙의 기존 객체는 그대로 두고 슬롯의 참조만 새 객체(`0x002`)로 바뀐다](assets/ChangeDetection/image_2.png)

전역 변수는 모든 함수에서 접근할 수 있어야 하므로 프레임에 저장되지 않는다. 대신 모듈 단위의 `f_globals` 딕셔너리에 `{변수명: 참조}` 형태로 저장된다.

![전역 변수 — f_globals 딕셔너리가 변수명별로 힙 객체의 참조를 담는다](assets/ChangeDetection/image_3.png)

여기에 객체의 가변성도 고려해야 한다. `int`, `str` 같은 불변 객체는 내용을 직접 수정할 수 없으므로, 값을 바꾸려면 새 객체를 재할당해 참조를 바꾸는 수밖에 없다. 반면 `list`, `dict` 같은 가변 객체는 참조는 그대로 두고 내용만 바뀔 수 있다.

## 단축 평가 엔진

위 참조 모델을 바탕으로, 비용이 적은 검사부터 차례로 수행하는 네 단계 판정을 만들었다.

```
1. 참조 동일성이 바뀌었는가? -> 바뀜 (재할당 확정)
2. 불변 타입인가? -> 안 바뀜 (제자리 변경 불가)
3. 컨테이너 크기가 달라졌는가? -> 바뀜 (전체 비교 불필요)
4. 값을 비교한다 -> 바뀜 / 안 바뀜
```

1. **참조 동일성**: 재할당이 일어나면 슬롯의 참조가 반드시 바뀐다. 따라서 포인터를 한 번 비교하는 것만으로 재할당을 확인할 수 있고, 값은 볼 필요가 없다.
2. **불변 타입 조기 종료**: 불변 객체는 내용을 수정할 수 없으므로, 1단계에서 참조가 같았다면 값도 같다. `int`, `str`, `float`, `bool`, `None`은 여기서 판정이 끝난다. 가장 자주 쓰이는 타입들이라 많은 판정이 이 단계에서 끝난다.
3. **크기 비교**: 여기까지 오는 것은 참조가 그대로인 가변 객체뿐이다. `list`, `dict`, `set`, `tuple`은 길이가 다르면 바로 변경으로 판정하므로, O(n) 비교를 O(1) 검사로 대신할 수 있다. 다만 크기가 같다고 값까지 같다고 할 수는 없으므로, 이 단계에서 "안 바뀜"으로 판정하지는 않는다.
4. **값 비교**: 참조와 크기가 모두 같은 가변 객체는 `PyObject_RichCompareBool`로 값 전체를 비교한다. O(n) 비용은 이 단계까지 온 경우에만 든다.

## 파이썬에서 먼저 거르는 경우

C 함수 호출에도 비용이 들기 때문에, `VariableTracker.evaluate`는 C 엔진을 부르기 전에 한 번 더 거른다. 원자 타입(`int`, `float`, `bool`, `complex`, `str`, `bytes`, `None`)은 `_make_state`에서 스냅샷을 만들지 않는다. `state["copy"]`가 `None`이면 참조만 비교하고 C 엔진은 호출하지 않는다.

`state["copy"]`가 `None`인 경우는 두 가지다. 원자 타입이라 처음부터 스냅샷이 필요 없었거나, `deepcopy`를 시도했지만 실패한 경우다. 둘은 `state["copy_failed"]` 플래그로 구분한다.

`threading.Lock`, 파일 핸들, 소켓, 제너레이터처럼 `deepcopy`할 수 없는 값이나, 그런 값을 안에 담은 컨테이너는 타입 검사로 미리 걸러내지 않는다. 중첩된 구조 안에 있는 복사 불가 객체를 빠짐없이 미리 찾아낼 방법이 없기 때문이다. 대신 `_make_state`는 `deepcopy`를 `try/except`로 감싸고, 실패하면 `copy`를 `None`으로 두고 `copy_failed`를 `True`로 설정한다.

두 경우 모두 `copy`가 `None`이므로 `evaluate`는 참조만 비교한다. 원자 타입은 내용을 직접 수정할 수 없으니 이것으로 충분하다. 하지만 복사에 실패한 값은 실제로 가변 객체일 수 있어서, 참조는 그대로인 채 내용만 바뀌는 변경은 감지하지 못한다. 이 한계는 의도적으로 받아들였다. 변경을 놓치는 편이 트레이스 콜백에서 예외를 던져 추적 대상 프로그램을 멈추게 하는 것보다 낫다고 판단했기 때문이다.

## 예외 격리

이슈 #52에서는 같은 원칙을 `deepcopy` 실패 외의 경우로 넓혔다. 4단계 값 비교(`PyObject_RichCompareBool`)에서 추적 중인 값의 `__eq__`나 `__ne__`가 예외를 던지면 결과로 `-1`이 반환된다. 이 예외는 `TraceDispatcher`의 check-and-log 경로(`_check_and_log_local`, `_check_and_log_global`, `_check_and_log_enclosing`)를 거쳐 `sys.settrace` 콜백 밖, 즉 사용자 코드로 그대로 전파될 수 있었다.

지금은 `_guarded_check_and_log`가 모든 check-and-log 호출을 트래커와 이벤트 단위로 감싼다. `register()`와 `_process_frame()`은 모두 `_check_tracker`를 거쳐 검사하고, 감싸는 일은 `_check_tracker`가 한다. 그래서 한 트래커의 비교가 계속 실패해도 다른 트래커와 이후 이벤트에는 영향이 없다.

저장할 때도 같은 원칙을 적용한다. `deepcopy`는 되지만 JSON으로 직렬화할 수 없는 값(일반 사용자 정의 객체 등)이 `data` 필드에 있으면, 예전에는 `HistoryBuffer.write`의 `json.dumps` 호출이 실패했다. 이 호출은 `atexit` 훅 안에서 실행되어 예외가 드러나지 않았고, 그 실행의 로그 파일 전체가 0바이트로 남았다.

지금은 `HistoryBuffer._serialize_entry`가 먼저 항목을 그대로 직렬화해 본다. 실패하면 `default=repr`로 다시 시도해 직렬화할 수 없는 값만 문자열로 바꾼다. `__repr__` 자체가 예외를 던지는 것처럼 이마저 실패하는 경우에만 그 항목 하나를 건너뛴다.

## C 확장으로 구현한 이유

위 판정은 줄마다 실행되므로, 파이썬으로 작성하면 판정에 드는 시간이 추적 대상 코드의 실행 시간보다 길어질 수 있다. 그래서 스코프 조회, 참조 비교, 타입 검사, 크기 비교, 값 비교는 `oscilo_engine`에서 C로 처리한다. 스냅샷 생성(`deepcopy`)과 이벤트 기록은 파이썬에 두어 C가 관리할 상태를 최소화했다.

## 초기 설계에서 바뀐 점

처음에는 C에서 `f_localsplus`(프레임의 참조 배열)와 `f_globals`에 직접 접근해 메모리를 추적하려 했다. 그런데 Python 3.11부터 이 필드들에 공식 API로 접근할 수 없게 되었다. 비공식 경로를 쓰면 파이썬 버전마다 깨질 위험이 있어서, 속도를 조금 포기하고 파이썬 네임스페이스에서 조회하는 방식으로 바꿨다. C 확장이 스코프 조회에 `PyObject_GetItem`과 `PyDict_GetItem`을 쓰는 것도 이 때문이다.

## 튜플도 깊은 복사하는 이유

원자 타입이 아닌 값은 `copy.deepcopy`로 스냅샷을 만든다. 튜플 같은 불변 컨테이너도 마찬가지다. 튜플 안에 가변 객체가 들어 있을 수 있기 때문이다. `t = ([1], [2])`에서 `t[0].append(3)`을 실행하면 `t`의 참조와 크기는 그대로지만 값은 바뀐다. 얕은 복사를 쓰면 원본과 스냅샷이 같은 리스트를 가리키게 되어 이 변경을 놓친다.

대신 깊은 복사 비용이 든다. 이 비용은 처음 관측할 때와 변경이 감지됐을 때만 들고, 변경이 없는 줄에서는 복사가 일어나지 않는다.

## 스냅샷을 복사해서 반환하는 이유

`get_snapshot()`은 저장된 스냅샷을 그대로 주지 않고 한 번 더 깊은 복사해서 반환한다. 호출한 쪽에서 반환값을 수정하면 비교 기준값까지 바뀌어 이후 비교가 모두 틀어지기 때문이다. `HistoryBuffer.getHistory()`도 같은 이유로 깊은 복사본을 반환한다.

이 두 번째 `deepcopy`도 실패할 수 있다. `__deepcopy__`가 원본과 다른, 그 자체로는 복사할 수 없는 객체를 반환하는 경우다. 이때는 `_make_state`에서 처음 복사에 실패했을 때와 똑같이 `copy`를 `None`으로, `copy_failed`를 `True`로 바꾼다. 이후 `evaluate`는 이 값을 참조 비교만으로 처리한다.

스냅샷 복사에 실패한 값은 객체의 `repr()` 대신 `<uncopyable>`이라는 고정 문자열로 기록한다. 따라서 객체 주소처럼 실행마다 달라지는 정보가 로그에 포함되지 않는다.

## Python 3.13+ 대응

Python 3.13부터는 `frame.f_locals`가 프록시 객체로 노출될 수 있어서, C 코드에서 버전에 따라 조회 방식을 나눈다.

- 3.13 이상: `PyObject_GetItem` (프록시 통과)
- 그 미만: `PyDict_GetItem` (borrowed reference → `Py_XINCREF` 필요)

## 이벤트 분류

| 이벤트 | 조건 |
|---|---|
| `init` | 이전 상태 없음 (첫 관측) |
| `updated` | 참조 또는 값 변경 |
| `no_change` | 변경 없음 (기록하지 않음) |
| `deleted` | 스코프에서 사라짐 (이전 상태 있었음) |
| `not_found` | 스코프에 없고 이전 상태도 없음 (기록하지 않음) |

`no_change`를 기록하지 않기 때문에, 로그 크기는 실행된 줄 수가 아니라 실제로 변경된 횟수에 비례한다.
